# Headless-оркестрация: постановка задач харнессу

## Роли

- **Оркестратор** (внешний агент/человек): формулирует задачу, принимает результат,
  независимо верифицирует. Токены оркестратора не тратятся на генерацию артефакта.
- **Исполнитель** (dsh + DeepSeek): работает с файловой системой и командной строкой,
  генерирует артефакты, отчитывается.

## Режим headless

Плагин `dsh-headless` (входит в базовую поставку) — one-shot режим:

```bash
cd <проект> && dsh --profile headless "<текст задачи>"
```

Контракт режима:

- один запуск = одна задача, без интерактивного продолжения;
- финальный ответ — в **stdout**, цепочка рассуждений — в stderr (`dsh: reasoning:`);
- процесс не открывает портов и ничего не оставляет работать;
- **exit 0** — задача завершена, **exit 1** — aborted/error (`dsh: <код>: <сообщение>` в stderr);
- пустой или whitespace-only текст задачи — usage error до запуска.

Это идеальный интерфейс для скриптов/CI/оркестратора: конвейер просто ждёт процесс.

## Структура текста задачи (порядок значим)

1. **Проверяемые критерии приёмки.** Каждый критерий проверяем исполнением
   («тесты X проходят», а не «код хорошего качества»). Принятие — только когда
   выполнен **каждый** критерий.
2. **Ground truth дословно.** Контракты и эталоны — содержимым файла или точным
   списком путей, которые исполнитель читает своими инструментами. Пересказ
   эталона в тексте задачи запрещён: исполнитель дрейфует и выдумывает
   собственные контракты.
3. **Границы.** Точный список файлов для создания/правки; запрет трогать систему
   сборки и структуру каталогов (CMakeLists, Cargo.toml, манифесты), если задача
   не про них; stdlib-first.
4. **Интеграция (integrity-блок)** против галлюцинаций — в конец текста задачи:

   ```text
   INTEGRITY: не утверждай, что что-то запущено/проверено/измерено, если ты
   этого не исполнял. Не выдумывай функции, флаги, поля API и пакеты — если
   не уверен, проверь (--help, документация, grep по исходникам) или скажи
   об неуверенности явно. Если данных недостаточно — скажи, чего не хватает,
   а не заполняй пробел правдоподобным текстом. Ошибки приводи дословно,
   причину — как гипотезу до подтверждения повторным запуском.
   ```

5. **Одна связная единица работы на запуск.** Взаимозависимые файлы одной цели
   сборки — одна задача: разбиение гарантирует падение сборки по причинам,
   не связанным с качеством кода. Несколько мелких задач лучше одной гигантской.
6. **Бюджет вывода.** Для правки существующих больших файлов — требовать
   локальные правки/дифф, а не переиздание файла целиком: у вывода модели есть
   жёсткий потолок, и полное переиздание большого файла будет тихо обрезано
   (эмпирически: файл ~84 КБ обрезался в 10 попытках из 10).

## Отличие от безинструментных воркеров

Классическая схема (например, LangGraph-оркестратор с безинструментными воркерами)
запрещает воркеру *симулировать* исполнение вовсе — прежде всего потому, что он
физически не может исполнять; реальные логи захватывает Python-харнесс, и только
они считаются доказательством (маркер вывода харнесса).

dsh — **агент с инструментами**: он реально запускает команды и тесты. Но его нарратив
об исполнении всё равно не доказательство. Схема переносится так: **харнесс — это
аудитор**; единственное доказательство — независимый перезапуск аудитом в чистом
процессе (см. [04-audit-methodology.md](04-audit-methodology.md)).

directory create lru_cache.py implementing class LRUCache (stdlib only: get/put,
capacity>=1, evicts LRU, get refreshes recency) and test_lru_cache.py with
unittest covering: eviction order, get-refreshes-recency, update existing key,
