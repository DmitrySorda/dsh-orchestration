# Skill: dsh-orchestration — оркестрация DeepSeek Harness

Роли: я формулирую задачи, принимаю и аудирую; артефакты генерирует DeepSeek
через dsh. Отчёт dsh об успехе — заявление, требующее верификации, не факт
(эмпирия: воркеры выдумывали вывод `cargo test`).

## Постановка задачи (договор с исполнителем)

Паттерн: `cd <проект> && dsh --profile headless "<текст задачи>"` — ответ в
stdout, exit 0/1, одна задача за запуск, без портов.

Текст задачи обязан содержать (порядок значим):

1. **Проверяемые критерии приёмки** — каждый критерий проверяем исполнением
   ("тесты X проходят", не "код хорошего качества"). Accept only if EVERY
   criterion is clearly met.
2. **Ground truth дословно** — контракты/эталоны содержимым файла или точным
   списком путей для чтения инструментами. Пересказ эталона в тексте задачи
   запрещён: исполнитель дрейфует и выдумывает свои контракты.
3. **Границы**: точный список файлов, которые можно создавать/править; запрет
   трогать сборку/структуру (CMakeLists, Cargo.toml, manifest), если задача
   не про них; stdlib-first.
4. **Интеграционный блок (integrity), адаптированный из no-fabrication guard** —
   вставлять в конец текста задачи:

   ```
   INTEGRITY: не утверждай, что что-то запущено/проверено/измерено, если ты
   этого не исполнял. Не выдумывай функции, флаги, поля API и пакеты — если
   не уверен, проверь (--help, документация, grep по исходникам) или скажи
   об неуверенности явно. Если данных недостаточно — скажи, чего не хватает,
   а не заполняй пробел правдоподобным текстом. Ошибки приводи дословно,
   причину — как гипотезу до подтверждения повторным запуском.
   ```

5. **Один запуск = одна связная единица работы.** Взаимозависимые файлы одной
   цели сборки — одна задача (сплит гарантирует падение сборки не по качеству
   кода). Несколько мелких задач лучше одной гигантской.
6. **BUDGET GUARD** (имя из промпта планировщика оркестратора): у вывода модели
   жёсткий потолок — в оригинале ~60k токенов на одно сообщение, thinking
   включён. Для крупной правки существующего файла — требуй дифф/локальные
   правки (`str_replace_editor`), не переиздание целиком. Эмпирическая база
   перенесена с **воркера LangGraph** (проект C-Buck50: по записи
   диспетчер-скилла ~84КБ обрезался в 10+ попытках из 10; в orchestrator.toml
   смежный эпизод описан как «5 прогонов подряд») — для dsh это **перенесённая
   гипотеза, а не измерение**: полноту артефакта контролирует аудит (п. 3).
7. **Seed-дисциплина**: задачу ставь в существующее дерево проекта —
   исполнитель ДОРАБАТЫВАЕТ зелёное дерево, а не строит с нуля. Формулировки
   вида «перегенерируй всё» запрещены; при повторных задачах на тот же субъект
   указывай, что уже построено и принято (сквозная память по topic-слагам —
   см. документацию оркестратора).
8. **Необратимые действия — только через явное подтверждение** (B3/C8 доктрины
   оркестратора): удаление файлов, перезапись без бэкапа, force-push,
   DROP/TRUNCATE, сетевые вызовы, меняющие состояние удалённой стороны,
   публикация вовне. В тексте задачи такие действия запрещаются явно; если они
   нужны — их выполняет оркестратор сам после подтверждения пользователем.
   Делегирование задачи не делегирует полномочие на необратимое действие.

## Аудит ответа (моя роль — быть харнессом)

В классической схеме доверяют только блоку, захваченному реальным exec-харнессом.
У dsh такого маркера нет — **харнесс здесь я**, поэтому:

1. **Перезапуск независимо**: тесты/сборку гоняю сам в чистом процессе; читаю
   файлы сам. Отчёт dsh «OK» не принимается как доказательство.
2. **Дифференциальный тест** для алгоритмики: эталонная реализация (stdlib/
   OrderedDict/brute force) + 10–20k случайных операций + инварианты
   (размер, контракт, границы). Расхождение = reject с конкретным op-номером.
3. **Полнота**: файл заканчивается корректно (не обрывается); маркер обрезки
   проверяется, если его ставит инструмент/профиль (литерального маркера
   TRUNCATED у самого dsh нет — это сигнал из плейбука LangGraph, не артефакт
   dsh); пустой ответ = провал без глубокого разбора — и его нельзя приодевать
   в правдоподобную историю отказа.
4. **Adversarial-кейсы, которых не было в задаче**: граничные значения,
   валидация входов, то, что исполнитель не мог «подогнать» под критерии.
5. **Противоречия** (COLLECT_CONTRADICTION_GUARD): разные прогоны/кандидаты
   расходятся в факте или числе — показать оба, не выбирать молча и не
   усреднять; арбитраж третьей детерминированной проверкой.
6. **Фидбек-цикл** (из feedback_suffix/test_failure_suffix оркестратора): при
   отклонении результата — перезапуск с приложенным к задаче текстом «Твоя
   предыдущая попытка отклонена. Фидбек: <причина>» и реальной диагностикой
   (вывод failing-команды дословно). Попытки ограничены: 2–3 по умолчанию
   (как MAX_ATTEMPTS=2 + local retries в оригинале).
7. **Провал после лимита попыток** — явный отказ пользователю, не правдоподобная
   заглушка и не тихое «примерно готово».
8. **Provenance в финальном ответе** (обе половины SYNTHESIS_PROVENANCE_GUARD):
   (а) что сделал dsh, что проверено мной независимо, что передано как есть;
   непроверенное помечено, не сливается с проверенным в один уверенный текст;
   (б) ни одного нового факта/числа/утверждения, которых нет в проверенных
   результатах; ключевые доказательства (цитаты выводов, строки итога тестов)
   вставляются дословно и **проверяются на выживание** при финальном
   редактировании — пересказ «как должно выглядеть» вместо реального лога =
   фабрикация.

## Качество кода (гейты приёмки)

- Тесты обязательны и executed-by-me; покрытие заявленных критериев, не строк.
- Не принимается: выдуманные API/пакеты/флаги (в т.ч. риск typosquatting),
  хардкод путей/версий без проверки, молчаливая подмена контракта.
- «Должно сработать» — гипотеза, не факт; системное состояние не угадывается,
  а проверяется.

## Отличие от безинструментного оркестратора (LangGraph-стиль)

Там воркер БЕЗ инструментов и не может исполнить код — запрет симулировать
вывод абсолютен, а exec-харнесс на Python захватывает логи. dsh сам агент с
инструментами: он реально исполняет, но его нарратив об исполнении всё равно
не доказательство — доказательство только мой независимый перезапуск.
Для батч-прогонов/ночных фанаутов используйте отдельный оркестратор;
для интерактива и одиночных задач — этот скилл.
